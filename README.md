# GitLab Todo Watcher

一个持久化 DSH Bundle：在左侧栏添加 **GitLab Todo** 页面，由 Host 直接通过 `glab` 定时读取 Todo，并将需要处理的事项分派到真实 DSH Session。不再需要 Python 或外置轮询脚本。

## 使用

1. 确保 `glab` 已登录且能访问目标 GitLab。
2. 打开左侧 **GitLab Todo** 页面。插件默认停用，不会安装后立即创建 Session。
3. 在 **设置** 中配置轮询间隔、每轮上限与自动处理并发数（默认 2）；也可直接用页头的模型下拉选择新会话模型。确认后再启用自动轮询。
4. 状态栏下方通过 **Todo 列表 / 当前会话 / 工作区** Tab 切换：Todo 列表可区域滚动，带有 **评论中 @ 我** 标签的事项会进入自动处理范围；**当前会话** 展示插件分派过的全部会话（最多 50 条，含启动中/已入队/执行中/执行完成/执行失败状态与自动/手动来源），点击标题回源 GitLab，点击 **打开 Session** 进入对应会话；**工作区** 展示当前 dsh-desktop 注册的全部工作区及各工作区下的会话列表（见下文）。
5. Session 内的 Agent 只有在实际完成后，才会按提示调用 `POST /todos/:id/mark_as_done`。

## 内置轮询与识别规则

Host 每次轮询先通过 `glab api user` 获取并缓存当前用户 ID，再使用只读的 `glab api -X GET todos` 分页读取当前用户的待办，每页 100 条、最多 20 页。响应由 Host 直接解析、校验和归一化。

只有同时满足以下条件的 Todo 才属于“他人在评论中 @ 我”：

- `action_name` 为 `directly_addressed` **或 `mentioned`**：前者是 @ 出现在评论开头（直接称呼），后者是 @ 出现在评论正文中。**只认 `directly_addressed` 会漏掉所有“文中 @ 我”的评论**——这是 v2.5 之前部分提及未进入处理的原因。
- `target_url` 包含 `#note_<id>`：Todo 来源于评论，而不是 Issue/MR 描述。
- `author.id` 不等于当前用户 ID：自己的提及走规则跳过，不进入处理。

该规则不限制 Issue、WorkItem 或 MergeRequest。普通指派、评审请求和其他通知仅保留在列表中，不自动创建 Session。

**正文 @ 提及（非评论）**：URL 无 `#note_<id>` 锚点的 `mentioned`/`directly_addressed`（如 Issue/WorkItem/MR 正文里的 @）同样走规则跳过，直接标记完成，不开会话。

## 分类与处理规则

- **符合条件的评论直接提及**：在“启用轮询”和“自动创建 Session”同时开启时，按每轮上限选取 Todo 进入分派队列，由后台队列逐条分派。**自动处理并发数**（默认 2，可设 1–10）限制的是插件自动创建的 Session 中**同时处于运行状态**的数量：一个会话本次执行真正结算（回合完成或失败）后，队列才会启动下一条，跨轮次同样生效。手动点击“开 Session 处理/重新处理”是显式人工动作，不占用也不受该上限约束。

### 规则跳过（零模型调用）

开启 **流水线通知、自己 @ 自己、正文 @ 提及等规则噪声直接标记完成**（默认开启）后，三类 Todo 在轮询阶段由程序内直接执行 `mark_as_done`，记录为 **已跳过（规则）**，完全不经过模型，也不创建会话：

- **流水线通知**：`build_failed` 等 `NOISE_ACTIONS` 集合内的 action。
- **自己 @ 自己**：`directly_addressed`/`mentioned` 且作者就是当前用户的提及（评论或描述均算）。
- **正文 @ 提及**：他人 @ 我但 URL 无 `#note_<id>` 锚点（Issue/WorkItem/MR 正文等）。

每轮最多处理 20 条，标记失败的留到下一轮。他人的评论提及永远优先于规则跳过，不会被误杀。

### 快速预检

开启 **每轮轮询先并行快速预判**（默认开启）后，自动分派前的“是否需要处理”判断在**轮询阶段并行完成**（最多 3 条同时判断），而不是排在会话派发队列里串行等待：

- 判定不需要处理（纯感谢/客套、纯 +1 附和、无关闲聊、无需回应的通报、测试性提及）→ 直接 `mark_as_done`，记为 **已跳过（无需处理）**，不创建任何会话——比“开会话再让 Agent 关闭”更快也更省。
- 判定需要处理 → 进入派派队列；此时若并发槽空闲，会话**立即**创建，不再先等一次模型调用。
- **预检模型**可单独固定一个更快的轻量模型（未配置时跟随会话模型，再退回 Host 默认模型），新会话仍使用会话模型。
- 预检的任何失败（无 llm 服务、路由不可用、超时、输出不可解析）都保守判定为需要处理，照常开会话；手动分派不经过预检。

其他速度相关默认值：会话结算轮询间隔 5s → **3s**（更快检测回合结束、释放并发槽）；轮询间隔与每轮上限可在设置中调低/调高（如间隔 60s、每轮上限 4）进一步压缩新 Todo 的等待时间。
- 页面状态栏显示 **自动会话运行中 x/上限** 与 **排队待分派** 数量；页头提供模型快捷下拉，改动立即保存，无需打开设置。
- **符合条件的 MR 评论提及**：同样创建 Session，不再因为目标是 MR 而直接标记完成。
- **其他 MR**：不自动处理；人工点击“标记完成”时，插件执行 `glab api -X POST todos/:id/mark_as_done` 并记录为 `merge-request-done`。
- **其他类型或提及方式**：只保留在列表中，不自动处理；人工点击“开 Session 处理”时才创建 Session。
- 手动“立即检查”只刷新结果，不触发自动分派。
- 已接受的 Todo 可通过列表中的 **打开 Session** 进入对应会话；“重新处理”是显式人工动作。

## Session 处理后的回复与完成标记

每个处理提示词都会携带 Todo ID、原 note ID、目标 URL 和 note 作者，并明确要求：

1. 正常处理结束后，在原 note 所属的 discussion 中回复提出该 note 的人，说明处理结果、实际改动或阻塞原因，而不是只新建顶层评论。
2. 如果本次处理新建了 MR（由该 Session 创建）：按 JEV-GATE.md 完成 Jev 裁决并留痕，且该 MR 的 CI 全部通过后，**直接合并该 MR，无需人类授权**——这是对工作区「合并 main 须人类授权」规则在插件会话中的显式豁免，仅适用于该 Session 新建的 MR。Jev 裁决或 CI 未通过时不得合并，修复重跑后仍不过则保留 MR 并说明原因；非该 Session 创建的 MR 不适用。
3. 只有实际完成该 Todo 后，才运行 `glab api -X POST todos/<todo-id>/mark_as_done`，仅标记当前这一条 Todo。
4. 无法完成或需要人类决策（上述 MR 合并授权除外）时，不运行完成命令；正常情况下仍应在原 note 回应进度和阻塞原因。

## DSH 会话交互（对齐 dsh-task-board 实现）

插件与 DSH 的全部会话操作都经 **typertGateway** 以 Host 本地 owner peer 调用（`session/modelCatalog|create|rename|selectModel|prompt|list|page` 与流式 `session/follow`），不使用浏览器传入的身份，与 [dsh-task-board](https://github.com/zhu1090093659/dsh-web/tree/main/packages/dsh-task-board) 的 HostExecutionRunner 同一调用契约。

**执行结算**：prompt 入队只代表“已接受”，不是完成。Host 定期（默认 5 秒，仅在有运行中会话或排队任务时轮询）读取会话名册：`running=true` 仍在执行；空闲后经 `session/follow` 开场帧与 `session/page` 有界回翻，找本次启动之后最早的 `turn/end`，只有 `data.reason.kind === 'completed'` 才记为执行完成，其余（error/interrupted/max-tokens 等）记为执行失败；名册读取失败一律视为“仍在执行”，绝不误判为空闲。连续 24 轮读不到历史才按失败收口，避免永久占用。

**完成后自动归档**：开启 **执行完成后自动归档会话**（默认开启）时，插件创建的会话在回合结算为完成后由内置轮询直接调用 `workspace/archiveSession` 归档（不带 `stopActivity`，仍有工作在跑会被 Host 拒绝并记录原因，绝不强行停止）。归档边界由数据结构保证：轮询只跟踪插件自己分派并记录在 `state.json` 的会话，任何非插件会话都不在跟踪集合中，永远不会被归档。归档失败或被拒不影响执行结算；失败的会话不自动归档，保留供人工查看；可在设置中关闭。

**并发槽位**：只有插件自动分派的会话计入并发上限；槽位从会话创建占用到本次执行真正结算（完成/失败/消失），跨轮次生效。手动“开 Session 处理”是显式人工动作，不计入也不受上限约束，但执行中禁止再次重新处理同一 Todo。

## 工作区总览

**工作区** Tab 以 `session/list` 名册（跟随 cursor 分页枚举全部已存储会话，含 cwd 与运行状态）为**主要数据源**驱动分组：会话按 cwd 精确匹配工作区路径，其次最长前缀匹配（会话开在工作区子目录内也归入该工作区），都不命中时进入「未归属工作区的会话」桶；`workspaceRegistry` 的 `sessionIds` 仅作补充（名册缺项时仍以 known=false 列出）。

不直接依赖 registry 实体的 `sessionIds` getter，因为它会按内部头索引过滤——旧会话或头文件不可解析的会话会被悄悄丢弃，导致非插件会话不显示。每个工作区卡片显示：

- 工作区名称与路径、会话数量、最近活动时间；被设置为“新开会话的工作区”的条目带 **插件目标** 标签。
- 该工作区下的全部会话（按最近活动倒序）：运行/空闲状态、最近活动时间；插件自己分派的会话带 **插件** 标签并显示会话标题，已归档的显示 **已归档** 且不可点击打开；空白草稿不展示。非插件会话只能查看与打开，永远不会被归档或修改。
- 「未归属工作区的会话」桶收纳 cwd 不属于任何已注册工作区的会话。

名册暂时不可用时自动降级为只展示注册表登记的会话（known=false），不影响其他功能。

## 新会话配置

- **新开会话的工作区**：下拉直接选择 DSH 已注册的工作区（列出名称与路径，来自 `workspaceRegistry`），或选择 **自动（最近使用的工作区）**；选定值仍以工作区路径保存在 `sessionCwd` 中，经 `workspaceRegistry` 解析为 `workspaceId` 传给 `session/create`。未注册的历史配置会显示为“当前配置（未注册）”并保留原值，命中失败会显式报错，绝不落回 Host 进程目录。它与 **GitLab 工作目录** 相互独立。
- **新开会话使用的模型**：直接遍历 Host 模型目录返回的全部模型分组；创建 Session 后依次执行 `session/rename`（标题形如 `[协助]-issue-7-note-10`，按目标类型 issue/workitem/mr/epic 与 note ID 命名，非标准链接退回 URL 最后两段）与 `selectModel({ provider, model })`，再提交提示词。选择具体模型（包括“固定当前默认模型”）会固定该路由，不随 DSH 默认模型变化。
- 设置保存在 `state.json`，不修改已接受的历史 Session。工作区只在创建时确定；pending Session 重试会复用原工作区，但会重新应用当前模型配置。

## 存储与升级

设置、Todo 去重和 Session 链接保存在 `~/.dsh-plugins/gitlabtodo/state.json`，采用原子写入，重启后恢复。插件不再创建 `gitlab-todos.py`、临时脚本目录或脚本编辑区域。

旧版 v1/v2 状态会在首次启动时自动升级为 v3：移除 `shell`、`script` 设置，保留 Todo、已处理记录、Session 链接和其他设置。

## 去重与失败恢复

- 空结果不创建 Session。
- 只有提示词入队成功后，Todo ID 才进入已处理记录（`executionStatus=running`），避免下一轮重复开会话。
- Session 已创建但提示词未入队时，记录 pending Session，下轮复用而不是重复创建。
- Host 重启后会从持久记录恢复仍在运行的会话监控，继续按回合结果结算。
- 每轮自动创建数量可设为 1–10；剩余新 Todo 留到后续轮次。

## Bridge 安全

页面通过同源 `/api/gitlab-todo-agent` 与 Host 通信，路由注册在 DSH `connection.fetch` 上。Connection 统一完成 Host/Origin 检查、签名 Cookie 认证和 Owner Peer 校验，插件不另开无认证端点，也不自行读取或保存浏览器凭据；响应禁止缓存。
